Python Runtime Fundamentals

Complete low-level analysis of CPython execution model, PyObject headers, 3-tier pymalloc, GC trial deletion, vectorcall protocols, generator frame suspension, zero-cost exception tables, and OS kernel interaction.

Day 1 Execution Model, Pipeline, Frames & Scope

1. Source Code to Bytecode Compilation Pipeline

When Python source code (.py) is executed, it passes through four distinct runtime phases:

  • Lexer: Converts raw UTF-8 text into a token stream (Parser/tokenizer.c).
  • PEG Parser: Builds Concrete Syntax Tree (CST) & AST (Parser/parser.c).
  • Symbol Table: Determines scopes (local, global, cell, free) (Python/symtable.c).
  • Bytecode Compiler: Emits 16-bit wordcode instructions into a Code Object (Python/compile.c).

2. Code Objects (PyCodeObject)

Bytecode instructions are immutable executable data wrapped in a C structure defined in Include/code.h: 

struct PyCodeObject {
    PyObject_HEAD
    int co_argcount;            /* Positional arguments count */
    int co_posonlyargcount;     /* Positional-only arguments count */
    int co_kwonlyargcount;      /* Keyword-only arguments count */
    int co_nlocals;             /* Local variables count */
    int co_stacksize;           /* Maximum evaluation stack depth needed */
    int co_flags;               /* Interpreter flags (CO_OPTIMIZED, CO_NEWLOCALS, etc.) */
    PyObject *co_code;          /* Raw opcode 16-bit wordcode byte sequence */
    PyObject *co_consts;        /* Tuple of literal constants used in bytecode */
    PyObject *co_names;         /* Tuple of global/attribute names referenced */
    PyObject *co_varnames;      /* Tuple of local variable names */
    PyObject *co_freevars;      /* Tuple of closure free variable names */
    PyObject *co_cellvars;      /* Tuple of local variables referenced by inner nested functions */
};
import dis
def add(a, b): return a + b

print(add.__code__.co_varnames)   # ('a', 'b')
print(add.__code__.co_argcount)   # 2
print(add.__code__.co_consts)     # (None,)
dis.dis(add)                       # disassemble bytecode

3. Execution Frames (PyFrameObject)

While PyCodeObject stores static bytecode instructions, stateful function execution occurs inside a PyFrameObject allocated on the C-heap (Include/frameobject.h):

struct PyFrameObject {
    PyObject_VAR_HEAD
    struct PyFrameObject *f_back; /* Linked list pointer to caller's frame (Python call stack) */
    PyCodeObject *f_code;         /* Pointer to PyCodeObject executed in this frame */
    PyObject *f_builtins;         /* Built-in namespace dictionary */
    PyObject *f_globals;          /* Global namespace dictionary */
    PyObject *f_locals;           /* Local namespace dictionary/mapping */
    PyObject **f_valuestack;      /* Pointer to evaluation stack bottom */
    int f_lasti;                  /* Index of last executed bytecode instruction */
    int f_state;                  /* Frame execution state (created, executing, suspended, cleared) */
    PyObject *f_localsplus[1];    /* Dynamic array for local variables, cell variables, and evaluation stack */
};
import sys, traceback

def show_frame():
    frame = sys._getframe()
    print(frame.f_code.co_name)       # 'show_frame'
    print(frame.f_back.f_code.co_name)  # caller's name

def a(): b()
def b(): c()
def c(): traceback.print_stack()  # Trace the LIFO frame stack
a()

4. C Stack vs Python Frame Stack

C Call Stack: Standard OS native thread stack managed by CPU hardware registers (ESP/RSP). Native C functions (e.g. PyEval_EvalFrameDefault in Python/ceval.c) push C stack frames during runtime execution.

Python Frame Stack: Linked list of PyFrameObject nodes allocated on the dynamic C-heap linked via f_back pointers.

Key Insight: Python frame objects reside on the heap rather than the native C thread stack. This architectural decoupling allows coroutines and generator frames to pause, remain in memory after C functions return, and resume execution seamlessly. Recursion depth limit (default 1000) is a soft constraint set via sys.setrecursionlimit().

5. Scope & Name Resolution (LEGB)

  • Local (L): Direct array indexing into f_localsplus via LOAD_FAST at O(1) speed.
  • Enclosing (E): Accesses cell objects (PyCellObject) via LOAD_DEREF.
  • Global (G): Hash lookup in f_globals dict via LOAD_GLOBAL.
  • Built-in (B): Fallback hash lookup in f_builtins dict.

Scoping Keywords: global x binds a name to module global scope; nonlocal x binds to nearest enclosing scope.

⚠️ Closure Late Binding Trap: funcs = [lambda: i for i in range(3)] returns 2 for all calls because i is captured by reference. Fix by binding at definition time: lambda i=i: i.

6. Global Interpreter Lock (GIL) & Thread State

The GIL (PyThread_type_lock) enforces atomic execution by allowing only one OS thread to run bytecode per interpreter state. Each thread owns a PyThreadState holding its frame stack, exception state, and thread ID. Threads releasing the GIL during blocking kernel I/O operations (file, socket, time.sleep) allow concurrency across threads.

8. Variable Reference Semantics & Mutability

Variables in Python do not contain values directly — they hold memory reference pointers (PyObject*) targeting heap objects:

a = [1, 2, 3]
b = a
b.append(4)
print(a)      # [1, 2, 3, 4] -- Shared mutable heap list payload

# Identity (is) vs Equality (==)
x = [1, 2]
y = [1, 2]
print(x == y)  # True (Equal value state)
print(x is y)  # False (Distinct memory reference pointers)

# Rebinding vs Mutation
a = [1, 2]
b = a
a = [3, 4]   # rebinds 'a', 'b' still points to original [1, 2]
print(b)     # -> [1, 2]

Day 2 Python Object Model, Memory Management & Garbage Collection

Day 2 focuses on what a Python object actually is in CPython, how objects are stored and referenced in memory, and how Python manages memory automatically via reference counting, small-object allocators, and cyclic garbage collection.

1. The Python Object Model

Everything in Python is an object — integers, strings, lists, functions, classes, and modules. Unlike C or Java where primitive types exist separately, Python treats all data uniformly as objects. Every object contains three core properties:

  • Identity (id()): Unique memory address pointer in C-heap space.
  • Type (type()): Defines the data structure and supported operations.
  • Value: The actual state or data payload contained inside the object.
x = 10
print(id(x))    # e.g. 140475290845232 (Memory Address)
print(type(x))  # <class 'int'>
print(x)        # 10

2. What is a PyObject?

Internally in CPython, every object begins with a C structure header named PyObject (defined in Include/object.h): 

typedef struct _object {
    _PyObject_HEAD_EXTRA        /* Doubly-linked list pointers used only in DEBUG builds */
    ssize_t ob_refcnt;           /* 64-bit Reference Count */
    struct _typeobject *ob_type; /* Pointer to object Type Object */
} PyObject;

typedef struct {
    PyObject ob_base;           /* Standard PyObject base header */
    ssize_t ob_size;            /* Item count in variable-length objects (lists, tuples, strings) */
} PyVarObject;
=================================================================================== CPYTHON OBJECT MEMORY LAYOUT (PyObject Header) =================================================================================== For x = 100 (Integer Object): +---------------------------------------------------------------------------------+ | PyObject Header: | | ob_refcnt : 1 | | ob_type : Pointer to PyLong_Type (<class 'int'>) | +---------------------------------------------------------------------------------+ | Value Payload: 100 | +---------------------------------------------------------------------------------+ For name = "Tony" (String Object): +---------------------------------------------------------------------------------+ | PyVarObject Header: | | ob_refcnt : 1 | | ob_type : Pointer to PyUnicode_Type (<class 'str'>) | | ob_size : 4 (length) | +---------------------------------------------------------------------------------+ | Value Payload: "Tony" | +---------------------------------------------------------------------------------+

3. Type Objects & Metaclasses (PyTypeObject)

An object's behavior, memory footprint, and operator methods are dictated by its type object (ob_type), defined in Include/object.h:

struct _typeobject {
    PyVarObject ob_base;
    const char *tp_name;        /* Type name string (e.g., "int", "list") */
    ssize_t tp_basicsize;       /* Instance base size in bytes */
    ssize_t tp_itemsize;        /* Dynamic item size for variable length types */
    destructor tp_dealloc;      /* C destructor called when ob_refcnt drops to 0 */
    getattrfunc tp_getattro;    /* Attribute access slot */
    setattrfunc tp_setattro;    /* Attribute assignment slot */
    reprfunc tp_repr;           /* String representation handler */
    PyNumberMethods *tp_as_number;   /* Math operator function pointers (+, -, *, /) */
    PySequenceMethods *tp_as_sequence;/* Indexing and slicing function pointers */
    PyMappingMethods *tp_as_mapping;  /* Key-value lookup function pointers */
    allocfunc tp_alloc;         /* Memory allocation function pointer */
    newfunc tp_new;             /* Constructor allocation (__new__) */
    initproc tp_init;           /* Instance initializer (__init__) */
};
print(type(5))     # <class 'int'>
print(type(int))   # <class 'type'>
print(type(str))   # <class 'type'>

4. Reference Counting Mechanics

CPython manages memory primarily via reference counting (ob_refcnt). Py_INCREF(op) increments the counter on variable binding or insertion; Py_DECREF(op) decrements it. When ob_refcnt reaches 0, CPython immediately invokes op->ob_type->tp_dealloc(op) to free memory or return it to memory pools. 

import sys

a = [1, 2, 3]  # Reference Count = 1
b = a          # Reference Count = 2
c = a          # Reference Count = 3

print(sys.getrefcount(a))  # Output: 4 (sys.getrefcount creates a temporary 4th reference)

del b          # Reference Count = 2
del c          # Reference Count = 1
del a          # Reference Count = 0 -> Memory freed immediately!

5. Three-Tier Memory Allocator (pymalloc)

To avoid frequent OS syscall overheads (malloc/free) for small objects (≤ 512 bytes), CPython implements a custom 3-tier memory allocator (Objects/obmalloc.c):

=================================================================================== CPYTHON 3-TIER PYMALLOC ARCHITECTURE =================================================================================== [ Tier 3: Python High-Level Application Objects (dict, list, int, str, frame) ] │ (PyObject_New / PyObject_GC_New) v [ Tier 2: pymalloc Small Object Allocator (Objects <= 512 bytes) ] ┌──────────────────────────┴──────────────────────────┐ Arenas (256 KB) Large Objects (> 512B) └─ Pools (4 KB) └─ Standard C malloc() └─ Blocks (8 to 512 bytes, 8-byte aligned) │ v [ Tier 0: OS Kernel Virtual Memory Manager (mmap / brk / VirtualAlloc) ]

6. Small Int Singletons, String Interning & Free Lists

  • Small Integer Cache (-5 to 256): CPython pre-allocates an array of singletons at bootstrap. All variable bindings in this range share exact memory address pointers.
  • String Interning (PyUnicode_InternInPlace / sys.intern()): Identifier names are interned in a global dictionary, enabling $O(1)$ fast pointer comparison (is) in C.
  • Object Free Lists: Recycles memory buffers for floats, tuples, lists, and frame objects to bypass allocator churn.
import sys

a = 5
b = 5
print(a is b)  # True (Reuses cached singleton)

s1 = "hello"
s2 = "hello"
print(s1 is s2)  # True (String interning active)

s3 = "hello world!"
s4 = "".join(["hello", " world!"])
print(s3 is s4)  # False (Distinct heap instances, same value)

s5 = sys.intern(s4)
s6 = sys.intern("hello world!")
print(s5 is s6)  # True (Explicit sys.intern)

7. Mutable vs. Immutable Objects

  • Immutable: int, float, str, tuple, frozenset. Modifications create brand-new objects on the heap.
  • Mutable: list, dict, set. In-place mutations modify existing object payloads directly.

8. Generational Cyclic Garbage Collection (Modules/gcmodule.c)

Reference counting cannot free circular reference chains (e.g. a references b and b references a). CPython uses a tri-generational cyclic garbage collector (Gen 0, Gen 1, Gen 2) with tracked objects prepended with a PyGC_Head header: 

typedef union _gc_head {
    struct {
        uintptr_t gc_next;
        uintptr_t gc_prev;
    } list;
    double dummy; /* Force 8-byte memory alignment */
} PyGC_Head;

Trial Deletion Algorithm:

  1. Copies ob_refcnt to a temporary gc_refs field for candidate containers in a generation.
  2. Traverses internal object pointers (tp_traverse) and decrements gc_refs of child objects.
  3. Objects left with gc_refs == 0 are candidate unreachable objects.
  4. Identifies root-reachable objects (gc_refs > 0) and promotes them along with their transitive closure.
  5. Unreachable cycles invoke finalizers (tp_finalize / __del__), break cycles, and execute tp_dealloc.
import gc

a = []
b = []
a.append(b)  # Circular reference
b.append(a)

del a
del b        # Refcount > 0 due to internal cycle!

gc.collect() # Triggers trial deletion sweep & frees unreachable cycle
=================================================================================== GENERATIONAL CYCLIC GC (TRIAL DELETION FLOW) =================================================================================== Candidate Containers (PyGC_Head Header Prepended) [Gen 0 (Young)] ──> [Gen 1 (Middle)] ──> [Gen 2 (Old)] │ ├──> 1. Copy ob_refcnt -> gc_refs for candidate containers ├──> 2. Traverse tp_traverse & decrement target gc_refs └──> 3. If gc_refs == 0: Isolate Unreachable Cycle ──> tp_finalize & PyObject_GC_Del

Day 3 Parser, AST, Bytecode Wordcode & Name Resolution

Day 3 explores the complete lifecycle of Python code execution — from parsing source text into an Abstract Syntax Tree (AST), compiling AST into 16-bit wordcode bytecode, executing stack-based instructions on the Python Virtual Machine (PVM), to variable lookups via LEGB scope rules.

1. Abstract Syntax Tree (AST) & AST Optimization

Before generating instructions, CPython's PEG parser converts source code into an Abstract Syntax Tree representing the program's structural hierarchy. You can inspect the tree using the ast standard library module:

import ast

code = "x = 10 + 20"
tree = ast.parse(code)
print(ast.dump(tree, indent=4))

# AST Transformer example:
class LoggingTransformer(ast.NodeTransformer):
    def visit_FunctionDef(self, node):
        log_stmt = ast.parse('print("Entering: ' + node.name + '")').body[0]
        node.body.insert(0, log_stmt)
        return node
=================================================================================== ABSTRACT SYNTAX TREE (AST) VISUALIZATION =================================================================================== Module └── Assign ├── Target: Name(id='x', ctx=Store()) └── Value: BinOp ├── left: Constant(value=10) ├── op: Add() └── right: Constant(value=20)

AST Optimization (Python/ast_opt.c): CPython performs constant folding at compile time. For instance, constant mathematical expressions like 3600 * 24 are evaluated and folded into 86400 directly inside the AST prior to bytecode generation.

2. Bytecode & Disassembly (dis module)

The Python Virtual Machine (PVM) is a stack-based virtual engine executing 16-bit instructions (1 byte opcode, 1 byte argument). Inspect bytecode with dis.dis():

import dis

def add(a, b):
    return a + b

dis.dis(add)

Common bytecode opcodes:

  • LOAD_CONST: Pushes a literal constant value onto the evaluation stack.
  • STORE_FAST: Pops top-of-stack and writes to local variable array f_localsplus at O(1) speed.
  • LOAD_FAST: Pushes local variable from f_localsplus array onto stack.
  • BINARY_ADD: Pops top 2 stack elements, computes addition, and pushes result.
  • RETURN_VALUE: Pops top-of-stack and returns it to the calling frame.
  • EXTENDED_ARG: Prepended opcode when an instruction argument value exceeds 255 (1 byte), combining arguments into 16, 24, or 32-bit values.

3. Evaluation Loop & Direct Threaded Dispatch (ceval.c)

The PVM evaluation loop runs inside PyEval_EvalFrameDefault() (Python/ceval.c). In optimized builds (GCC/Clang), opcode dispatch uses computed goto (direct threaded code) for maximum throughput:

/* Direct Threaded Code Dispatch in ceval.c */
static void *targets[] = {
    &&TARGET_NOP,
    &&TARGET_LOAD_FAST,
    &&TARGET_STORE_FAST,
    ...
};
goto *targets[opcode];

Step-by-step evaluation stack execution for result = 5 + 7:

=================================================================================== PVM EVALUATION STACK EXECUTION STEP-BY-STEP =================================================================================== Step 1: LOAD_CONST 5 Step 2: LOAD_CONST 7 Step 3: BINARY_ADD Step 4: STORE_FAST result | | | 7 | | | | | | 5 | | 5 | | 12 | | (empty)| +-------+ +-------+ +--------+ +--------+ Stack: [5] Stack: [5, 7] Stack: [12] result = 12

4. 16-Bit Wordcode Layout & Adaptive Opcodes (PEP 659)

In Python 3.11+, PyEval_EvalFrameDefault dynamically transforms generic opcodes like LOAD_GLOBAL into specialized adaptive instructions (LOAD_GLOBAL_MODULE / LOAD_GLOBAL_BUILTIN) to cache dictionary version tags and bypass dictionary hashing.

=================================================================================== 16-BIT WORDCODE INSTRUCTION LAYOUT (Python 3.11+) =================================================================================== +-------------------------------------+-------------------------------------+ | Opcode (1 Byte / 8-bit) | Argument (1 Byte / 8-bit) | +-------------------------------------+-------------------------------------+ =================================================================================== PEP 659 ADAPTIVE OPCODE SPECIALIZATION FLOWCHART =================================================================================== PyEval_EvalFrameDefault() Bytecode Loop │ Check Warm Counter / Adaptive State / \ (Cold) / \ (Warm - Specialize) v v Generic Opcode Specialized Opcode (e.g. LOAD_GLOBAL_MODULE) - Hashing Dict - Checks Cached Version Guard - Search globals - Fetches Value via Direct C Array Pointer O(1)

5. Scope & Name Resolution (LEGB Rule)

Variable lookups strictly follow the LEGB hierarchy:

  1. Local (L): Direct array indexing into f_localsplus via LOAD_FAST at O(1) speed.
  2. Enclosing (E): Accesses cell objects (PyCellObject) via LOAD_DEREF.
  3. Global (G): Hash lookup in f_globals dict via LOAD_GLOBAL.
  4. Built-in (B): Fallback hash lookup in f_builtins dict.
x = "Global"

def outer():
    x = "Enclosing"
    def inner():
        nonlocal x   # Modifies enclosing scope variable
        x = "Modified Enclosing"
    inner()
    print(x)  # Output: Modified Enclosing

outer()
⚠️ Compile-Time Scope Determination: Python decides whether a variable is local at compile time. Assigning to a variable anywhere in a function body makes it local throughout the entire function scope, causing UnboundLocalError if read before assignment.

Day 4 Function Objects, Vectorcall, Closures & Default Args

Day 4 dives into how Python functions operate as first-class objects, function object internals (__code__, __defaults__), closure mechanics (PyCellObject), decorator patterns, *args/**kwargs unpacking, and the classic mutable default argument trap.

1. Functions as First-Class Objects

Functions in Python can be assigned to variables, stored in collections, passed as arguments, and returned from other functions:

def add(a, b):
    return a + b

def multiply(a, b):
    return a * b

ops = [add, multiply]
print(ops[0](2, 3))  # 5
print(ops[1](2, 3))  # 6

2. Function Internals (PyFunctionObject) & Vectorcall (PEP 590)

When defining a function, CPython instantiates a PyFunctionObject defined in Include/funcobject.h: 

typedef struct {
    PyObject_HEAD
    PyObject *func_globals;     /* Active global namespace dictionary */
    PyObject *func_builtins;    /* Active builtin namespace dictionary */
    PyObject *func_name;        /* Function __name__ string */
    PyObject *func_code;        /* Underlying PyCodeObject pointer */
    PyObject *func_defaults;    /* Tuple of positional default argument values */
    PyObject *func_kwdefaults;  /* Dict of keyword-only default values */
    PyObject *func_closure;     /* Tuple of PyCellObject pointers for free variables */
    PyObject *func_annotations; /* Type annotations dictionary */
    vectorcallfunc vectorcall;  /* Vectorcall fast C-style function pointer */
} PyFunctionObject;
def greet(name, greeting="Hello"):
    return f"{greeting}, {name}"

print(greet.__name__)                # 'greet'
print(greet.__defaults__)            # ('Hello',)
print(greet.__code__.co_varnames)    # ('name', 'greeting')

The Vectorcall Fast-Call Protocol (PEP 590) optimizes call sites by passing function arguments as a raw C array pointer (PyObject *const *args), bypassing intermediate tuple/dict heap allocations and GC overhead.

3. Closure Mechanics & Cell Objects (PyCellObject)

A closure is an inner function that retains access to variables from its enclosing lexical scope even after the outer function frame has popped from the stack. Shared free variables are wrapped in heap-allocated PyCellObject instances (Include/cellobject.h):

typedef struct {
    PyObject_HEAD
    PyObject *ob_ref; /* Pointer to shared heap object */
} PyCellObject;
def power(n):
    def calculate(x):
        return x ** n
    return calculate

square = power(2)
cube = power(3)

print(square(5))  # 25
print(cube(5))    # 125

# Inspect closure cell value:
print(square.__closure__[0].cell_contents)  # Output: 2

4. Decorators & Wrapper Patterns

A decorator is a higher-order function that takes a function object, wraps it with additional behavior, and returns the modified wrapper function:

import functools

# Function Decorator Factory with arguments
def retry(times=3):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    if attempt == times - 1: raise
        return wrapper
    return decorator

@retry(times=5)
def flaky_operation():
    pass

# Class-Based Decorator Pattern
class Cache:
    def __init__(self, func):
        self.func = func
        self.cache = {}
        functools.wraps(func)(self)  # Copy metadata (__name__, __doc__)
    def __call__(self, *args):
        if args not in self.cache:
            self.cache[args] = self.func(*args)
        return self.cache[args]

@Cache
def expensive_compute(n):
    return n * n

Common real-world decorator applications: Logging, Authentication/Authorization, Timing/Profiling, Caching (functools.lru_cache), Input Validation, and Retry Logic.

5. Variadic Parameters (*args & **kwargs)

  • *args: Packs extra positional arguments into a tuple.
  • **kwargs: Packs extra keyword arguments into a dict.
  • Positional-only parameters (before /): def f(a, b, /, c): ...
  • Keyword-only parameters (after *): def f(a, *, b): ...

6. The Mutable Default Argument Trap

Default parameter values are evaluated once when the function module is loaded into memory, storing the default objects in func_defaults. If you use a mutable object like [] or {} as a default, every invocation reuses and mutates the exact same instance! 

# ❌ BUG: Reuses single list instance from func_defaults
def add_item_bad(item, items=[]):
    items.append(item)
    return items

print(add_item_bad("A"))  # ['A']
print(add_item_bad("B"))  # ['A', 'B'] -- Unexpected shared state!

# ✅ FIX: Use None sentinel and create new list per invocation
def add_item_good(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items

print(add_item_good("A"))  # ['A']
print(add_item_good("B"))  # ['B'] -- Clean independent state!

=================================================================================== VECTORCALL FAST-CALL PROTOCOL (PEP 590) =================================================================================== Standard Call (Slow): Caller ──> Create (args, kwargs) Tuple & Dict ──> Function Entry (GC Overhead) Vectorcall (Fast O(1)): Caller ──> Pass Raw C Array Pointer: PyObject *const *args + Flags ──> Function Entry =================================================================================== CLOSURE CELL RESOLUTION (PyCellObject) =================================================================================== Outer Scope (popped frame): Inner Scope (active function): +--------------------------+ +--------------------------+ | outer_func() frame | | inner_func Object | | x = 42 | | func_closure tuple | +--------------------------+ +--------------------------+ \ / v v +-----------------------------------------------------------+ | PyCellObject | | [ob_refcnt = 1] │ [ob_ref] ──> PyLongObject (42) | +-----------------------------------------------------------+

Day 5 Iteration Protocol, Generator Frames & Suspension

Day 5 explores how Python iterates over collections, generator frame allocation on the C-heap, suspension/resumption mechanics via YIELD_VALUE, sub-iterator delegation via yield from, and comprehension scope isolation.

1. The Iteration Protocol Mechanics

The iteration protocol relies on two C function pointers ("slots") defined inside PyTypeObject:

  • tp_iter: C function pointer returning an iterator object (invoked via PyObject_GetIter(obj)).
  • tp_iternext: C function pointer returning the next item (invoked via PyIter_Next(iter)) or returning NULL when exhausted. 
class CountUp:
    def __init__(self, max_val):
        self.max_val = max_val
        self.n = 0
    def __iter__(self):
        return self
    def __next__(self):
        if self.n >= self.max_val:
            raise StopIteration
        self.n += 1
        return self.n

for x in CountUp(3):
    print(x) # 1, 2, 3

Under the hood, for x in obj: compiles to:

_iter = iter(obj)          # calls obj.__iter__()
while True:
    try:
        x = next(_iter)    # calls _iter.__next__()
    except StopIteration:
        break

2. Generator Object Structure (PyGenObject)

Generators are stateful stack-frame wrappers defined in Include/genobject.h:

typedef struct {
    PyObject_HEAD
    PyFrameObject *gi_frame;    /* Heap-allocated execution frame pointer */
    char gi_running;            /* Flag indicating whether generator is executing */
    PyObject *gi_code;          /* Code object pointer */
    PyObject *gi_yieldfrom;     /* Active sub-iterator pointer during yield from */
} PyGenObject;

3. Suspension and Resumption Mechanics & Generator Protocols

Function Invocation: Calling a generator function instantiates a PyGenObject wrapping gi_frame and returns it immediately without executing frame bytecode (gi_frame->f_state = FRAME_CREATED).

Executing next(gen) / send(): Sets gi_running = 1 and enters PyEval_EvalFrameDefault(gi_frame). Execution runs until encountering YIELD_VALUE.

Generator Communication Protocols:

  • gen.send(value): Resumes generator and passes value into the yield expression.
  • gen.throw(exc): Raises exception inside generator at current yield point.
  • gen.close(): Raises GeneratorExit inside generator for cleanup.
def accumulator():
    total = 0
    while True:
        val = yield total
        if val is None: break
        total += val

gen = accumulator()
next(gen)              # Prime generator -> 0
print(gen.send(10))    # 10
print(gen.send(20))    # 30
gen.close()            # Close generator

4. Sub-Iterator Delegation (yield from)

yield from iterable delegates iteration directly inside ceval.c:

def flatten(matrix):
    for row in matrix:
        yield from row  # Delegates sub-iteration directly to row iterator

def chain(*iterables):
    for it in iterables:
        yield from it

print(list(chain([1, 2], [3, 4]))) # [1, 2, 3, 4]

5. Comprehension Internals & Generator Expressions

# List Comprehension: Builds full heap list (PyList_New) in memory O(N)
squares_list = [x**2 for x in range(1000)]

# Generator Expression: Evaluates lazily on-demand with O(1) memory complexity
squares_gen = (x**2 for x in range(1000))
print(next(squares_gen))  # 0
print(next(squares_gen))  # 1

Day 6 Context Managers, Zero-Cost Exceptions & Kernel Resources

Day 6 covers context manager protocols (__enter__ / __exit__), Python 3.11 zero-cost exception tables, exception stack unwinding mechanics, and OS kernel file descriptor management.

1. Context Manager Protocol & `contextlib`

Context managers implement two protocol methods:

  • __enter__(self): Prepares resource setup and returns context target object.
  • __exit__(self, exc_type, exc_val, exc_tb): Guarantees teardown cleanup execution regardless of whether errors occurred. Return True to suppress exceptions.
from contextlib import contextmanager, suppress, ExitStack

class Timer:
    import time
    def __enter__(self):
        self.start = self.time.perf_counter()
        return self
    def __exit__(self, *args):
        self.elapsed = self.time.perf_counter() - self.start
        return False  # Do not suppress exceptions

@contextmanager
def temp_dir():
    import tempfile, shutil
    d = tempfile.mkdtemp()
    try:
        yield d
    finally:
        shutil.rmtree(d) # ALWAYS executes cleanup

with temp_dir() as d:
    pass

# Utility tools in contextlib:
with suppress(FileNotFoundError):
    import os; os.remove("missing.txt")

# ExitStack for dynamic variable number of resources
def process_multiple(paths):
    with ExitStack() as stack:
        files = [stack.enter_context(open(p)) for p in paths]
        # All opened files automatically closed on exit

2. Zero-Cost Exception Tables (co_exceptiontable in Python 3.11+)

Prior to Python 3.11, setup opcodes like SETUP_WITH pushed block entries onto f_blockstack at runtime. In Python 3.11+, blockstacks are replaced by static co_exceptiontable tables mapping bytecode instruction ranges to handler landing pads, eliminating setup opcode overhead on normal execution paths.

3. Exception Raising, Unwinding & Exception Chaining

# Exception Chaining with 'from'
try:
    connect_database()
except ConnectionError as e:
    raise RuntimeError("Service initialization failed") from e
    # Sets __cause__ and preserves original traceback
  1. Raising Error: PyErr_SetObject() stores exception type, value, and traceback in active PyThreadState.
  2. Table Lookup: Evaluation loop halts linear execution and performs binary search in active frame's co_exceptiontable for current offset f_lasti.
  3. Local Handler Match: If handler pad exists, adjusts stack depth, pops intermediate objects (Py_DECREF), and jumps f_lasti to handler landing pad.
  4. Frame Unwinding: If no handler exists in current frame, executes active __exit__ blocks, pops frame, decrements refcount, and propagates unwinding up f_back linked list.
  5. Unhandled Exit: If top of stack is reached unhandled, prints traceback to stderr and terminates process.

4. Kernel File Descriptors & Resource Leak Prevention

# ❌ DANGEROUS: Relying on GC for cleanup risks file descriptor leak if trapped in cycle!
f = open("data.txt", "w")
f.write("payload")
# Missing f.close() -> OS file descriptor remains open until GC runs

# ✅ SAFE: Deterministic cleanup via context manager
with open("data.txt", "w") as f:
    f.write("payload")
# __exit__ ALWAYS executes close(fd) syscall immediately upon block exit

5. Cleanup and Safe Finalizers (weakref.finalize())

⚠️ Avoid __del__ for Resource Teardown: __del__ methods can delay GC, fail during interpreter shutdown, or resurrect dead objects. Use weakref.finalize() for non-blocking cleanup routines. 
import weakref

class DatabaseConnection:
    def __init__(self, db_id):
        self.db_id = db_id
        weakref.finalize(self, DatabaseConnection._close_id, db_id)

    @staticmethod
    def _close_id(db_id):
        print(f"Closed database connection {db_id}")

Day 7 End-to-End Program Execution Lifecycle & Review

Day 7 synthesizes the complete end-to-end lifecycle when executing python main.py, tracking process initialization from kernel space down to C runtime bootstrap, bytecode compilation, opcode loop execution, and process teardown.

1. Detailed 5-Phase Execution Architecture

  1. Phase 1: OS Kernel Process Initialization:
    User executes python main.py. Shell issues execve("/usr/bin/python3", ...) syscall. OS kernel ELF loader maps binary into Virtual Memory space (.text, .data, heap, C stack). Execution transfers to C main() in Programs/python.c.
  2. Phase 2: CPython Runtime Bootstrap (Py_Initialize):
    Allocates PyInterpreterState and main PyThreadState. Bootstraps pymalloc pools & arenas. Initializes static type objects (PyLong_Type, PyList_Type, etc.). Initializes sys module (sys.modules, sys.path) and builtins dictionary. Creates GIL mutex (PyThread_type_lock).
  3. Phase 3: Source Code Compilation Pipeline:
    Opens script file via kernel open() syscall. Lexer (tokenizer.c) emits token stream; PEG Parser (parser.c) builds AST; Symbol Table (symtable.c) resolves variable scopes; Bytecode Compiler (compile.c) emits top-level PyCodeObject.
  4. Phase 4: Evaluation Loop & OS Syscalls:
    Instantiates root module PyFrameObject on C-heap. PyEval_EvalFrameDefault() fetches 16-bit wordcodes. a = 100 allocates PyLongObject via pymalloc. print("hello") extracts bytes buffer, calls C fwrite(), issuing kernel write(1, "hello\n", 6) syscall to stdout FD 1.
  5. Phase 5: Runtime Teardown & Exit (Py_FinalizeEx):
    Reaches RETURN_VALUE. Runs final cyclic GC sweep across all generations. Clears sys.modules, releases GIL, frees memory pools. C main() issues OS kernel exit_group(0) syscall to reclaim virtual memory pages.

3. Key Interview Questions & Answers

Q: What happens under the hood when you call a function in Python?
A: CPython instantiates a PyFrameObject linked to the function's PyCodeObject, pushes it onto the LIFO frame stack via f_back, maps arguments into the f_localsplus array, and executes 16-bit opcodes inside PyEval_EvalFrameDefault.
Q: How does CPython manage memory?
A: Primary mechanism is Reference Counting (immediate deallocation when ob_refcnt == 0). Secondary mechanism is Generational Cyclic GC (Gen 0/1/2 trial deletion) for circular references. Small objects (≤ 512B) use pymalloc Arenas/Pools/Blocks.
Q: Why are closure variable lookups slower than local variables?
A: Local variables use LOAD_FAST (O(1) direct array index in f_localsplus). Closure variables use LOAD_DEREF, which requires dereferencing a PyCellObject indirection pointer.
Q: Explain the default mutable argument gotcha.
A: Default argument values are evaluated once at definition time and stored in func_defaults. Mutable defaults (like []) are shared across all invocations; mutations persist between calls.
