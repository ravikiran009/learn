MODULE 01

Python Runtime Fundamentals

Complete low-level analysis of CPython execution model, PyObject headers, 3-tier pymalloc, GC trial deletion, vectorcall protocols, generator frame suspension, zero-cost exception tables, and OS kernel interaction.

Day 1 Execution Model, Pipeline, Frames & Scope

1. Source Code to Bytecode Compilation Pipeline

When Python source code (.py) is executed, it passes through four distinct runtime phases:

  • Lexer: Converts raw UTF-8 text into a token stream (Parser/tokenizer.c).
  • PEG Parser: Builds Concrete Syntax Tree (CST) & AST (Parser/parser.c).
  • Symbol Table: Determines scopes (local, global, cell, free) (Python/symtable.c).
  • Bytecode Compiler: Emits 16-bit wordcode instructions into a Code Object (Python/compile.c).

2. Code Objects (PyCodeObject)

struct PyCodeObject {
    PyObject_HEAD
    int co_argcount;            /* Positional arguments count */
    int co_nlocals;             /* Local variables count */
    int co_stacksize;           /* Evaluation stack max depth */
    PyObject *co_code;          /* Raw opcode byte sequence */
    PyObject *co_consts;        /* Tuple of literal constants */
    PyObject *co_names;         /* Tuple of global/attribute names */
    PyObject *co_varnames;      /* Tuple of local variable names */
    PyObject *co_freevars;      /* Tuple of closure free variable names */
    PyObject *co_cellvars;      /* Tuple of local variables referenced by inner scopes */
};

3. Execution Frames (PyFrameObject)

struct PyFrameObject {
    PyObject_VAR_HEAD
    struct PyFrameObject *f_back; /* Linked list pointer to caller frame */
    PyCodeObject *f_code;         /* Static bytecode instructions pointer */
    PyObject *f_builtins;         /* Builtins dict */
    PyObject *f_globals;          /* Globals dict */
    PyObject *f_locals;           /* Locals dict */
    PyObject **f_valuestack;      /* Value stack bottom pointer */
    PyObject *f_localsplus[1];    /* Dynamic array for locals, cells, stack */
};

4. C Stack vs Python Frame Stack

Python evaluation frames are NOT stored on the native OS thread C stack. They are linked-list nodes allocated on the dynamic C-heap. This architectural decoupling enables coroutines and generator frames to pause and remain in memory after C functions return.

5. Scope & Name Resolution (LEGB)

  • Local (L): Direct array indexing into f_localsplus via LOAD_FAST at O(1) speed.
  • Enclosing (E): Accesses cell objects (PyCellObject) via LOAD_DEREF.
  • Global (G): Hash lookup in f_globals dict via LOAD_GLOBAL.
  • Built-in (B): Fallback hash lookup in f_builtins dict.

6. Global Interpreter Lock (GIL) & Thread State

The GIL (PyThread_type_lock) enforces atomic execution by allowing only one OS thread to run bytecode per interpreter state. Each thread owns a PyThreadState. Threads releasing the GIL during blocking kernel I/O operations allow concurrency.

7. Compilation & Frame Allocation Flowchart

Source (.py) ──> Lexer ──> Tokens ──> PEG Parser ──> AST ──> Symbol Table ──> PyCodeObject │ C-Heap Frame Allocation │ v +-------------------------------------------------------------------------------------------------------+ | PyFrameObject (Linked List Node on C-Heap) | | [f_back] ──> Pointer to caller's PyFrameObject | | [f_code] ──> Pointer to PyCodeObject (bytecode, co_consts, co_names) | | [f_globals] ──> Pointer to Globals dict | | [f_localsplus]──> Array: [Locals (O(1) LOAD_FAST)] [Cell Vars (LOAD_DEREF)] [Evaluation Stack] | +-------------------------------------------------------------------------------------------------------+
Day 2 PyObject, Memory Allocation & Cyclic GC

1. The PyObject C Header

typedef struct _object {
    ssize_t ob_refcnt;           /* 64-bit Reference Count */
    struct _typeobject *ob_type; /* Pointer to object Type Object */
} PyObject;

2. Three-Tier Memory Allocator (pymalloc)

=================================================================================== CPYTHON 3-TIER PYMALLOC ARCHITECTURE =================================================================================== [ Tier 3: Python High-Level Application Objects (dict, list, int, str, frame) ] │ (PyObject_New / PyObject_GC_New) v [ Tier 2: pymalloc Small Object Allocator (Objects <= 512 bytes) ] ┌──────────────────────────┴──────────────────────────┐ Arenas (256 KB) Large Objects (> 512B) └─ Pools (4 KB) └─ Standard C malloc() └─ Blocks (8 to 512 bytes, 8-byte aligned) │ v [ Tier 0: OS Kernel Virtual Memory Manager (mmap / brk / VirtualAlloc) ]

3. Small Int Singletons, String Interning & Free Lists

  • Small Integer Cache: Pre-allocates singletons for [-5, 257] during runtime bootstrap.
  • String Interning: Interns identifiers in a global dict to enable $O(1)$ C pointer equality checks.
  • Object Free Lists: Recycles memory buffers for floats, tuples, lists, and frames to bypass pymalloc calls.

3. Cyclic Garbage Collection (Modules/gcmodule.c)

Containers tracked by GC prepend a PyGC_Head doubly-linked list header, maintaining 3 generational lists (Gen 0, Gen 1, Gen 2) and executing Trial Deletion:

  1. Copies ob_refcnt to temporary gc_refs field for candidate objects.
  2. Traverses internal references and decrements gc_refs of target objects.
  3. Objects with gc_refs == 0 are isolated as unreachable cycles, finalized (tp_finalize), and deallocated.

4. Memory Allocation & GC Trial Deletion Flowchart

=================================================================================== GENERATIONAL CYCLIC GC (TRIAL DELETION FLOW) =================================================================================== Candidate Containers (PyGC_Head Header Prepended) [Gen 0 (Young)] ──> [Gen 1 (Middle)] ──> [Gen 2 (Old)] │ ├──> 1. Copy ob_refcnt -> gc_refs ├──> 2. Traverse tp_traverse & decrement target gc_refs └──> 3. If gc_refs == 0: Isolate Unreachable Cycle ──> tp_finalize & PyObject_GC_Del
Day 3 Parser, AST, Bytecode Wordcode & Name Resolution

1. 16-Bit Wordcode Architecture

Instructions consist of 2-byte units (1 byte opcode, 1 byte argument). Large arguments use EXTENDED_ARG prefix instructions.

2. Evaluation Loop & Adaptive Opcodes (PEP 659)

In Python 3.11+, PyEval_EvalFrameDefault dynamically transforms generic opcodes like LOAD_GLOBAL into specialized adaptive instructions (LOAD_GLOBAL_MODULE / LOAD_GLOBAL_BUILTIN) to cache dictionary version tags and bypass dictionary hashing.

3. Instruction Format & PEP 659 Adaptive Execution Flowchart

Day 4 Function Objects, Vectorcall, Closures & Default Args

1. Vectorcall Fast-Call Protocol

Replaces traditional tuple/dict creation by passing function arguments as a raw C array pointer (PyObject *const *args), drastically lowering GC pressure.

2. Closure Mechanics (PyCellObject)

Free variables shared between outer and inner scopes are wrapped inside heap-allocated PyCellObject instances. When outer execution frames pop, cell objects remain alive as long as inner functions reference them in func_closure.

3. Mutable Default Arguments Trap

Default parameters (e.g. def foo(a=[])) are evaluated once at module load time. The list pointer is stored in the function's func_defaults tuple on the heap and reused across all function invocations.

4. Vectorcall & Closure Cell Scope Resolution Flowchart

=================================================================================== VECTORCALL FAST-CALL PROTOCOL (PEP 590) =================================================================================== Standard Call (Slow): Caller ──> Create (args, kwargs) Tuple & Dict ──> Function Entry (GC Overhead) Vectorcall (Fast O(1)): Caller ──> Pass Raw C Array Pointer: PyObject *const *args + Flags ──> Function Entry =================================================================================== CLOSURE CELL RESOLUTION (PyCellObject) =================================================================================== Outer Scope (popped frame): Inner Scope (active function): +--------------------------+ +--------------------------+ | outer_func() frame | | inner_func Object | | x = 42 | | func_closure tuple | +--------------------------+ +--------------------------+ \ / v v +-----------------------------------------------------------+ | PyCellObject | | [ob_refcnt = 1] │ [ob_ref] ──> PyLongObject (42) | +-----------------------------------------------------------+
Day 5 Iteration Protocol, Generator Frames & Suspension

1. Generator Object Structure (PyGenObject)

typedef struct {
    PyObject_HEAD
    PyFrameObject *gi_frame; /* Heap-allocated execution frame */
    char gi_running;         /* Execution state flag */
    PyObject *gi_yieldfrom;  /* Pointer to sub-iterator during yield from */
} PyGenObject;

2. Suspension and Resumption

Encountering YIELD_VALUE saves the current instruction offset in gi_frame->f_lasti, sets state to FRAME_SUSPENDED, and returns control to the caller without destroying gi_frame from the C-heap.

3. Generator Frame Suspension & Resumption State Diagram

=================================================================================== GENERATOR EXECUTION STATE TRANSITION DIAGRAM =================================================================================== +---------------------------------+ | GEN_CREATED | (gi_frame allocated on C-Heap) +---------------------------------+ │ next() / send() v +---------------------------------+ | GEN_RUNNING | (PyEval_EvalFrameDefault active) +---------------------------------+ / \ YIELD_VALUE return / Exception / \ v v +---------------------------------+ +---------------------------------+ | GEN_SUSPENDED | | GEN_CLOSED | | - Save instruction offset f_lasti| | - Free gi_frame from C-Heap | | - Yield value back to caller | | - Set gi_frame pointer = NULL | | - Frame remains on C-Heap | +---------------------------------+ +---------------------------------+
Day 6 Context Managers, Zero-Cost Exceptions & Kernel Resources

1. Zero-Cost Exception Tables

Python 3.11+ replaces runtime SETUP_WITH block opcodes with static co_exceptiontable mappings, eliminating setup overhead during normal execution paths.

2. Kernel File Descriptors & Resource Management

Python file objects wrap OS File Descriptors (integers managed by kernel tables). Omitting with context managers risks leaking file descriptors if objects get trapped in cyclic GC lists, leading to EMFILE errors.

3. Zero-Cost Exception Handling & Kernel FD Cleanup Flowchart

Day 7 End-to-End Program Execution Lifecycle
  1. OS Kernel Process Initialization: Shell calls execve(), kernel maps binary into Virtual Memory address space (.text, .data, heap, C stack).
  2. CPython Runtime Bootstrap: main() invokes Py_Initialize(), setting up interpreter state, pymalloc, builtins, and GIL.
  3. Compilation Phase: Source text $\rightarrow$ Tokens $\rightarrow$ PEG AST $\rightarrow$ Symbol Table $\rightarrow$ PyCodeObject.
  4. Evaluation Loop Execution: PyEval_EvalFrameDefault() executes bytecode, managing objects via pymalloc and OS system calls.
  5. Teardown & Exit: Py_FinalizeEx() flushes streams, runs final GC sweep, releases memory, and issues OS exit_group().

Evaluation Frame & Opcode Loop] Allocates PyFrameObject on C-Heap ──> PyEval_EvalFrameDefault() ──> pymalloc & GC │ [5.
