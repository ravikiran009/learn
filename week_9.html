Day 58 Consensus Algorithms, Raft & etcd Leader Election

58.1 Raft Consensus Protocol

1. Candidate increments term -> sends RequestVote RPC to all peers. 2. Majority YES votes -> Node becomes LEADER. 3. LEADER accepts writes -> appends to log -> replicates via AppendEntries RPC. 4. When majority of followers ACK -> LEADER commits entry and responds to client!

58.2 Lease-Based Leader Election with etcd

import etcd3, time

client = etcd3.client()
lease = client.lease(ttl=10)

# Transactional key acquisition
success, _ = client.transaction(
    compare=[client.transactions.version('/service/leader') == 0],
    success=[client.transactions.put('/service/leader', 'node-1', lease=lease)],
    failure=[]
)
if success:
    print("I am the elected Leader! Periodically refreshing lease...")
    while True:
        lease.refresh()
        time.sleep(3)
Day 59 Caching at Scale: Hot Keys, Thundering Herds & XFetch

59.1 Hot Key Solutions

  • Local In-Memory Cache (L1): cachetools.TTLCache inside process memory bypasses Redis network bottleneck.
  • Probabilistic Early Expiry (XFetch): Refreshes hot key cache before expiration to eliminate cache miss stampedes.
  • Mutex Lock Pattern: First cache miss acquires Redis lock to populate data while concurrent requests wait.

60.1 Message Ordering & Idempotent Consumer

Kafka guarantees strict event ordering within a partition. Always set the message key to customer_id or order_id so all related events land in the same partition.

Day 61 Search Systems: Inverted Index & Elasticsearch BM25

61.1 Inverted Index & BM25 Relevance

An inverted index maps terms to document IDs ("python" -> [doc1, doc3, doc7]). Relevance ranking uses BM25 (Term Frequency $\times$ Inverse Document Frequency with document length normalization).

Day 62 Capacity Planning, Little's Law & System Design Numbers

62.1 Little's Law Formula

$$L = \lambda \times W$$

Where $L$ is concurrent requests in system, $\lambda$ is arrival throughput (req/s), and $W$ is average latency (seconds).
