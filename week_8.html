Day 50 Docker: Images, Layers, Volumes, Networking & Multi-Stage Builds

50.1 Container Primitives & Multi-Stage Dockerfile

Containers leverage Linux Namespaces (PID, NET, MNT, IPC) for isolation and cgroups to enforce memory and CPU resource limits.

# Build Stage
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# Production Stage (Minimal final image)
FROM python:3.12-slim AS production
RUN groupadd -r appuser && useradd -r -g appuser appuser
WORKDIR /app
COPY --from=builder /root/.local /root/.local
COPY . .
USER appuser
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
Day 51 Kubernetes: Control Plane, Pods, Deployments & Health Probes

51.1 Control Plane vs Worker Node Architecture

Control Plane: API Server <---> etcd (Cluster State Store) └─> Controller Manager & Scheduler Worker Nodes : kubelet <---> containerd / CRI-O <---> kube-proxy (Networking)

Day 53 StatefulSets, Persistent Volumes & K8s Operators

53.1 StatefulSets vs Deployments

Deployments manage stateless interchangeable pods with random hash IDs. StatefulSets manage stateful database clusters (PostgreSQL, Kafka, ZooKeeper) where each pod retains a stable ordinal identity (db-0, db-1) attached to its own persistent volume claim (PVC).

Day 54 Helm Charts & Rollout Deployment Strategies

54.1 Deployment Rollout Options

  • RollingUpdate: Replaces pods incrementally (zero downtime).
  • Blue-Green: Deploys v2 alongside v1, then switches load balancer target instantly.
  • Canary (Argo Rollouts): Shifts 5% → 25% → 100% of live production traffic to v2 while monitoring error rate metrics.
Day 55 GCP Infrastructure: Cloud Run, GKE, Pub/Sub & IAM Workload Identity

55.1 Serverless Cloud Run vs GKE

Cloud Run automatically scales HTTP container instances from 0 to N based on incoming requests (pay-per-use). GKE provides full Kubernetes cluster orchestration for complex microservice meshes and background stateful workers.

Workload Identity: Allows GKE pods to assume GCP Service Account roles natively without storing vulnerable JSON credential keys inside container images!

Day 56 Cloud Architecture Design Review
Q: What is the difference between Liveness and Readiness probes in Kubernetes?
A: A failing Liveness probe tells Kubernetes the container has deadlocked or crashed, causing kubelet to restart the container. A failing Readiness probe tells Kubernetes the container is temporarily busy or initializing, causing the service to temporarily stop routing traffic to that pod until it recovers.
