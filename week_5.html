Day 29 Advanced SQL: Joins, CTEs & Window Functions

29.1 Execution Algorithms for Joins

  • Nested Loop Join ($O(N \times M)$): Iterates over inner table for each row in outer table. Best when joining small tables or indexed lookups.
  • Hash Join ($O(N + M)$): Builds in-memory hash table on join key of smaller table, then probes it with larger table.
  • Merge Join ($O(N \log N + M \log M)$): Sorts both tables on join keys and merges concurrently.

29.2 Recursive CTEs for Hierarchical Graphs

WITH RECURSIVE org_hierarchy AS (
    -- Base Case: Root Executives
    SELECT id, name, manager_id, 1 AS depth
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    -- Recursive Step: Subordinates
    SELECT e.id, e.name, e.manager_id, oh.depth + 1
    FROM employees e
    JOIN org_hierarchy oh ON e.manager_id = oh.id
)
SELECT name, depth FROM org_hierarchy ORDER BY depth, name;

29.3 Window Functions

SELECT name, salary, department_id,
       ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) as row_num,
       DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) as dept_rank,
       LAG(salary, 1) OVER (PARTITION BY department_id ORDER BY hire_date) as prev_salary
FROM employees;

30.2 PostgreSQL MVCC (Multi-Version Concurrency Control)

In PostgreSQL, UPDATE operations do not overwrite existing tuples in-place. Instead, a new tuple version is created with xmin set to the current transaction ID, while the old tuple's xmax is updated. Readers read consistent snapshots without blocking writers!

Day 31 Indexes, B-Tree Structure & EXPLAIN ANALYZE

31.1 B-Tree Index Structure

B-Trees maintain balanced leaf nodes connected as a doubly linked list, enabling $O(\log N)$ point lookups as well as fast ordered range scans (e.g. WHERE salary BETWEEN 50k AND 100k).

31.2 Specialized Index Types

  • Covering Index: Uses INCLUDE (col1, col2) to allow Index-Only Scans without reading heap pages.
  • Partial Index: Indexes a filtered subset (e.g. WHERE status = 'pending') saving disk space.
  • GIN (Generalized Inverted Index): Used for array elements, JSONB documents, and full-text search.

31.3 Query Execution Plans

EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending' AND created_at >= NOW() - INTERVAL '1 day';
Day 32 Sharding, Streaming WAL Replication & Failover

32.1 Partitioning vs Sharding

Partitioning splits large tables into physical chunks within a single database node. Sharding distributes data horizontally across multiple independent database nodes using consistent hashing on a shard key.

32.2 Replication Tradeoffs

  • Synchronous Replication: Zero data loss (RPO = 0), but high commit latency waiting for standby ACK.
  • Asynchronous Streaming WAL Replication: Low commit latency, but potential replication lag on failover.

33.1 Cache-Aside (Lazy Loading) Pattern

import json, redis

r = redis.Redis(host='localhost', port=6379, db=0)

def get_user_profile(user_id):
    cache_key = f"user:{user_id}"
    cached_val = r.get(cache_key)
    if cached_val:
        return json.loads(cached_val)

33.2 Redis Eviction Policies

  • allkeys-lru: Evicts Least Recently Used keys when maxmemory is hit (best for general caches).
  • volatile-lru: Evicts LRU keys that have an explicit TTL set (best for session stores).
  • allkeys-lfu: Evicts Least Frequently Used keys based on access frequency counter.
Day 34 Distributed Databases & Spanner Consistency

34.1 CAP Theorem Matrix

CP (Consistency + Partition Tolerance) : etcd, Zookeeper, PostgreSQL (Sync) AP (Availability + Partition Tolerance) : Cassandra, DynamoDB (Eventual Consistency)

34.2 Google Spanner TrueTime API

Google Spanner uses synchronized atomic clocks and GPS receivers in every datacenter to provide the TrueTime API. By guaranteeing a tight time uncertainty bound ($\epsilon \le 1\text{ ms}$), Spanner enforces strict external serializability across global datacenters via commit wait!

Day 35 Query Optimization Workshop
Q: How do you fix a slow query performing a Sequential Scan on 10 million rows?
A: Run EXPLAIN ANALYZE to check predicate selectivity. Add a B-Tree index on filtered/joined columns. If the query retrieves only specific columns, create a covering index with INCLUDE to convert it to an Index Only Scan.
